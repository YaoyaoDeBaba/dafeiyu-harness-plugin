## 追加（2026-11-17 第二轮口头，趁 1.9 卡住时提出）

5. **原需求要常驻在右侧栏置顶**：用户要能随时回看、对照自己说过什么。现在需求只在
   `requirement.md` 里，界面上看不到原文。
   实现方向：`/state` 返回 `requirement`（原文），面板顶部折叠展示「需求原文」。
6. **跑单中点胶囊应打开右侧栏**（已打开则跳过），**不应弹出下单输入框**；下单入口只在
   「没有订单」或「订单已结束」时由胶囊承担。
   现状：胶囊永远切接单模式，跑单时点它反而盖住了聊天框。
7. **UI 提交后流程「停住」**：用户在面板点「提交给流程」→ 答案落盘 → **没人跑 `done`**，
   于是从用户视角看就是停住了（实际是等 Agent 交活）。
   实现方向（三选一，倾向 A+B）：
   - A. 提交后立刻在面板上写「已提交，等主 Agent 继续」，并把胶囊状态切到「等回复」的下一步；
   - B. 后端在收到答案后写一个 `<run>/ui-done-request.json`，Agent 侧（或后台 job）看到就跑 `done`；
   - C. 允许 UI 直接触发 `done`（危险：会绕过主 Agent 的表单核对，不建议）。

    ⚠ **「等待子代理返回」是一格状态，不是两格**（用户 2026-11-17 澄清）：
    这一格里要**列出当前在跑的子代理及其各自在干什么**（例如：exec-cloud3 在改云生成、exec-arc3 在改电弧段数），
    而不是写死「等 A 执行 / 等 B 执行」两种状态。
    目的：让用户确信它「有在工作」，并且知道**卡在谁身上**，而不是笼统地等。

14. **意图确认必须走界面表单，不许在聊天里问**（2026-11-17 用户提出）：
    这一轮的取色取舍（云底色冷/灰/折中）我是直接在聊天里问的，用户体验割裂——
    凡是需要用户拍板的取舍（包括**中途新增**的），都应进 `intent.confirm.json` 由右侧栏渲染成单选提交，
    聊天里只留一句「去右侧栏选」的指引。
    实现方向：主 Agent 侧加一条约定 + 后端一个 `POST /confirm` 允许任意阶段追加问题；
    前端把"待确认"角标打到胶囊上（等回复态）。
15. **吐槽必须保证被消费，不能只挂在 2.4b 一个钩子上**（2026-11-17 验证后提出）：
    现状：吐槽落 `user-interrupt.jsonl` 后，**只有** `done --stage 2.4b-userreview-rN` 会把它并进
    `user-review.json`。于是有三种漏法：
    - 预算里 `userReview=false` → 2.4b 不存在，吐槽永远不消费；
    - 订单在 2.4b 之前终止（decide 直接 stop / 用户手动结束）→ jsonl 滞留；
    - 并进 user-review 之后，是否进下一轮工单**取决于主 Agent 有没有读它**，程序不强制。
    要做：
    - 消费点至少再加两处：`2.5-decide` 交活时把未消费的吐槽并入 `decide.json.gapsForNextRound`；
      `3.1-summarize` 时把它们列进总结（"这轮你说过但没处理的"）。
    - 程序强制：`2.5-decide` 的 check 里，若 jsonl 有条目却不在 decide 的任何字段里出现 → 不放行。
    - UI 反馈：每条吐槽显示"将进第 N 轮工单 / 已并入评审 / 已过期"。
16. **吐槽输入框会被轮询刷新清空**（2026-11-17 用户实测）：
    面板每 3s 拉一次 `/state`，只要内容有变化就重建 `innerHTML`——`<textarea>` 的当前输入不属于 HTML，
    于是**写到一半的吐槽会丢**。
    修法（三条一起）：
    - 重绘前保存 textarea 的 value/选区，重绘后回填；
    - 或者把吐槽输入区移出重绘范围（固定节点 + 只更新状态行）；
    - 并且给"用户正在输入"加一个短暂静默窗（如 2s 内不重绘），避免边打字边被刷。
17. **下单时可分别指定「调查模型」与「执行模型」**（2026-11-17 用户提出）：
    - 需求输入框（接单模式）加两个下拉：**调查模型** / **执行模型**，选项从可用模型列表拉取；
    - 默认项是「由主 Agent 分配」（现在的行为：调查用 X、执行用 Y 由 plan 阶段决定）；
    - 用户指定了就按用户的——1.3/1.4/1.5 调查员与 2.2 执行员派活时必须用指定模型；
    - 需要落地：`/state.models`（或单独 `/models`）返回可派活的 {provider, model, label} 列表；
      `/start` 接收 `{researchModel, execModel}` 并存进 `budget.json` / `order.json`；
      plan 与派活模板读它，缺省才走主 Agent 分配。
    - 用户用例：下一次跑「mimo 执行 + kimi 调查」。
