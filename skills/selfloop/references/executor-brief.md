# 执行员交付规范（2.2-exec-rN 专用）

**什么时候读**：你被派成执行员、拿到 `tickets/2.2-exec-rN.json` 时；或本轮自迭代停下、准备交活前做交付自查时。
（主 Agent 读 `references/workflow.md`；这一篇只讲「怎么迭代、怎么停、怎么交」，不讲跨轮搜索。）

## 一、你是谁：做**有限**自迭代，不自跑跨轮闭环

- 跨轮闭环（活性扫描 → 选轴 → 搜索 → 判定 → 要不要下一轮）归**主 Agent**（2.1~2.5）。
- 你只做本轮工单里列的那些改动，**允许**在本轮内自迭代：改一版 → 出一帧 → 看差多少 → 再改。
- 但自迭代**有边界**：最多自调 `maxSelfIterations` 轮（默认 3；工单里写了就按工单）。到上限就停，交当前最好那版。
- 不写 `intent.json` / `plan.json` / `verify.json` / `decide.json`（那是主 Agent / 程序的活）。
- **每完成一项立刻落盘** `rounds/r<N>/NN.json`，别攒到最后一起写 —— 半路中断时那是唯一能救回的现场。

## 二、三条停止条件（满足**任一**即停，别硬调）

| # | 条件 | 口径 |
|---|---|---|
| ① | **达到判据** | 所有硬判据都在带内（不是「看起来接近」，是数值在目标区间里） |
| ② | **用满轮次预算** | 自迭代轮次到 `maxSelfIterations`（默认 3） |
| ③ | **平台期** | 连续 **2 轮无显著提升**：任一主判据改善 <5%，**或**与上一轮交付帧的平均像素差 <2% |

③ 怎么算：把这一轮的主判据值与上一轮比（改善幅度 / 上一轮值），再把两张帧逐像素平均差（0~1，或 0~255 归一）。两个都够小 = 平台期，**停**。

停在哪个条件上，交活说明里就写哪一条。**不许无限调**：实测过一次 exec-cloud5 拿着判据自己调到天亮，预算全耗在一个子代理身上。

## 三、停下时**如实交**（禁止「已优化」这种空话）

固定三件，一行写完：

```
当前值 <参数=实测值> ｜ 差多少 <目标 - 实际 = 差值> ｜ 卡在哪 <哪个约束/上限把路堵死了>
```

例：`当前值 cloudCoverage=0.42、平均亮度 0.51 ｜ 差多少 覆盖率差 0.43、亮度差 0.04 ｜ 卡在粒子发射上限：再加会把屋顶穿透（已知会破 invariants）`

「已优化 / 接近目标 / 基本达标」这种写法等于没交，主 Agent 与用户都没法判断下一步。

## 四、每轮自迭代留一行痕：`rounds/r<N>/iters.md`

每轮自迭代一行，别把过程只留在脑子里：

```md
| 轮 | 改了什么 | 判据 / 像素差 |
|---|---|---|
| 1 | 云层 density 0.6→0.8 | 覆盖率 0.31→0.42（目标 0.85） |
| 2 | 加一层 noise scale 0.5 | 覆盖率 0.42→0.47，与上轮帧像素差 3.1% |
| 3 | density 0.8→0.9 | 覆盖率 0.47→0.48（改善 2.1% <5%，已进平台期）→ 停 |
```

## 五、工作法（照着做，别靠手感）

这一节是从一个把云做出来的执行员身上扒下来的工作方式。**它不是性格，是可复制的动作**；照做比靠手感稳定。

| # | 规则 | 常犯的错 |
|---|---|---|
| 1 | **先读完再动手**：目标文件分块读完、场景先探针（有几个实例、哪些 active）、工具先确认存在 | 157 行的 shader 只读 40 行就开改，改完发现另有分支 |
| 2 | **一次一处**：改完立刻验（编译状态 + 控制台 + `GetShaderMessages`），绿了再改下一处 | 一次改 6 个参数，反向验证不出是哪个起作用 |
| 3 | **参数不生效就改假设**：连续两轮同一指标纹丝不动 → 停手，问「是不是我的因果模型错了」 | 「再加大力度试试」——把调参失败当成幅度不够 |
| 4 | **阈值来自分布**：任何阈值都要写清「哪个样本的哪个分位」（p5/p50/p95） | 「0.6 看着差不多」→ 后来发现整张图只有 ±0.02 的容差 |
| 5 | **怀疑量具**：掩膜、编码、路径、分辨率、场景里的静态残留对象 | 把棋盘地板算进云区，三轮都在跟地板较劲 |
| 6 | **承认夹逼**：两条判据互相冲突时明说可行域很窄，别假装都满足 | 「基本达标」——实际是把一条判据偷偷放宽了 |
| 7 | **每轮至少一次单变量判别实验**：用一帧 A/B 定性，比连调十轮省时 | 反复扫参，始终没分清「是混叠还是密度场本身」 |

第 3 条最值钱：**同一个指标两轮不动，就是模型错了，不是力度不够**。这时候再加参数只会掩盖问题。

第 7 条的做法：只动一个变量拍两帧（例：步数 32 vs 64），看主指标变化幅度——腰斩说明是那个变量，纹丝不动就排除它。**判别帧也算交付物**，命名带 `_ab_<变量>`。

## 六、交活三件套（缺一件 pipeline 会写 verify.caveat 留痕）

`done --stage 2.2-exec-rN` 时会核对 `rounds/r<N>/snapshot/`：

| 件 | 内容 |
|---|---|
| `code/` | 本轮改过的源文件（原样复制进去，别只写路径） |
| `scene-params.json` | 用 MCP 导出的组件字段 + 材质值（参数名 → 实机值），不是「我改成了 0.88」这种口头描述 |
| `params.md` | 本轮每个参数的**旧值 → 新值 → 为什么**（一行一条） |

随时手动快照：`node harness/snapshot.mjs --run <run目录> --tag <名字> [--file <改过的源文件>...] [--scene <导出.json>] [--params <参数说明.md>]`
（不带 `--tag` 就写进 `rounds/r<N>/snapshot/`。）

为什么必须留：今晚丢了用户认可的那版云 —— 代码能找回，参数与场景序列化值全丢，`cloudCoverage` 实机 0.88 没人知道何时被改的。

## 七、交付自检 4 条（交活说明里逐条写「查了 / 没查 + 数值」）

1. **贴完整帧**：给整帧，不裁剪、不局部放大；同时跑崩坏自检
   `node harness/crash-check.mjs <帧.png>`（exit 1 = 有洋红像素 / 纯色大块 / 全黑全白）。
2. **Unity 类目标**：`GetShaderMessages() == 0`（console 里没有 shader error / warning）；有 warning 也要贴出来。
3. **每项判据一行实测**：`判据 | 目标 | 实测 | 怎么量`，缺一项就写「未测 + 为什么」。
4. **每完成一项立刻写 rounds**：`rounds/r<N>/NN.json` 至少含 `shot`（或 preview）与 `changes[]`。

## 八、帧命名与索引

- 调试帧：`<stage>_<round>_<variant>_<t>.png`（例：`2.2-exec_1_base_320ms.png`）。名字里带时刻，别只写「第 16 帧」。
- 每次交付附 `frames.md`：这一轮出了哪几帧、每帧是什么变体、看哪张为准。

## 九、用 MCP 改现场的坑

- `mcp.ps1` 的 `-Json` 必须是 **Plain JSON**。多套一层转义会报 `Invalid property identifier`；报这个错先看是不是把 JSON 又 JSON 了一遍。
- 改完立刻回读一次实机值（组件字段 / 材质值），别信「发出去就等于生效」。

## 十、交活

```bash
node harness/crash-check.mjs rounds/r<N>/<帧>.png     # 自检：exit 0 才允许交
node harness/snapshot.mjs --run <run目录>              # 补三件套（缺什么它会告诉你）
node harness/pipeline.mjs done --run <run目录> --stage 2.2-exec-rN
```

pipeline 通过后会把「下一个节点」打出来；快照缺口会以 `verify.caveat` 留痕（不拦你，但会被主 Agent 与用户看到）。
