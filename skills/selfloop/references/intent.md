# 写或改 intent（需求转译闸）

**这份答案一个问题**：`intent.json` 怎么填、填错了会怎样。

**什么时候读**：跑之前要写/改 `intent.json`（判据 criteria、锚 anchors、用户原话 userWords / 量法 howMeasured），或者被 `[需求转译闸]` 挡下来要看懂错误原文。

**结论先说**：

1. `criteria` 里只写 `anchor`、既不给 `userWords` 也不给 `howMeasured` → **exit 1** 拒跑（等于凭空编指标）。
2. 给不出量化口径就写 `"暂无口径，靠参考图对照"` → 能跑，但台帐记 `degraded` + `[intent][warn]`。**不许编假精确数字**。
3. `anchors` 现在**不进搜索**（只进台帐与报告），别指望写了锚就更像参考图。
4. 硬不变量是**判废**（不进距离），不是扣分——它单独一篇：`invariants.md`；硬闸错误原文：`intent-errors.md`。

> **原总述（0.5.0 ~ 0.9.1 的来龙去脉，可跳读）**
>
> 两件东西解决的是同一个病：**这套引擎原来只有中段**。
> 需求转译、调研参考这两段根本没有节点，直接从中段（活性扫描 → 搜索）开始 —— 所以它"虚"不是缺界面，
> 是头两段不存在；而"被绕过"一直在发生（缺回读、参数判 dead、缓存命中、`repeat=1` 关掉稳定性闸），
> 只是散在日志里，没有一处汇总，于是"被绕过"这件事连名字都没有。
> 
> 0.5.0 做的是：**跑之前必须有一份经过确认的需求转译**（否则拒跑）、**每一步都落一条能机器读的台帐**。
> 0.5.1 做的是：把 intent 从 v1 升到 **v2**，补上 **锚 / 反例 / 自由度 / 验收方式** 四样（见 §1.5）。
> 0.9.0 做的是：**调研（research）成为真节点**（02 号，排在 intent 之后、target 之前）——
> 判据不是"搜了几条"，而是"**它有没有真的改变判据或起点**"（`changed`，由引擎自己算）。见 §2.5。
> 0.9.1 做的是：给每条 `criteria` 补 **`userWords`（用户原话）/ `howMeasured`（怎么量）**——
> 专治"编假指标"：观感词原样下发等于没说，而编一个看似精确的假指标会诱导搜索优化错方向。见 §1.8。

## 1. 需求转译（intent）怎么填

**放哪**：

| 链路 | 默认位置 | 能不能指别处 |
|---|---|---|
| 命令（`harness/cmdloop.mjs`） | `<out>/intent.json` | `--intent <file>` |
| 截图（`harness/iter.ps1`） | `<Out>\intent.json` | `-Intent <file>` |

### 1.1 v2 结构（照抄下面这份，改内容）

```json
{
  "version": 2,
  "restate": "火柱要更粗更硬，但别变成一根直线光",
  "anchors": [
    { "kind": "image", "ref": "refs/ref-a.png", "why": "同类高评分火焰特效" },
    { "kind": "text",  "ref": "崩坏：星穹铁道（具体游戏名，不是抽象风格）", "why": "配色与勾线参照" }
  ],
  "criteria": [
    {
      "id": "cov", "weight": 0.6, "target": 0.02,
      "anchor": "anchors[0]：参考图里的亮核占比",
      "userWords": "用户原话：火柱要更粗更硬，但别变成一根直线光",
      "howMeasured": "亮核像素数 ÷ 整幅像素数（mask = 色相在黄橙区间且 alpha > 0.5）",
      "why": "你说的'更粗'"
    },
    {
      "id": "lapVar", "weight": 0.2,
      "anchor": "anchors[1]：参考游戏里的边缘锐利度",
      "userWords": "用户原话：边缘要有锐劲，别糊成一坨",
      "howMeasured": "沿法线扫 alpha 25%→75% 的像素距离，越短越锐",
      "why": "细节次要"
    }
  ],
  "notWanted": ["不要写实/PBR 连续渐变", "不要像素噪点式的硬过渡"],
  "freeVsFixed": {
    "fixed": ["命中点的位置", "整体配色链（白芯→黄→橙→暗红）"],
    "free":  ["光束长度", "弯曲与摆动幅度", "火星密度"]
  },
  "howWeVerify": { "human": true, "metrics": true, "note": "指标过闸 + 人眼确认一次" },
  "uncertain": ["'更硬'是指边缘锐利还是对比度更高？"],
  "confirm": ["粗细优先还是亮度优先？"],
  "confirmed": true,
  "confirmedBy": "user",
  "confirmedAt": "2026-11-14T10:46:00+08:00"
}
```

### 1.2 v2 字段表

| 字段 | 是什么 | 硬要求 |
|---|---|---|
| `version` | intent 版本；**没有这个字段 = v1** | v2 写 `2`。不写 → 按 v1 跑、打 warn、台帐记 `degraded` |
| `restate` | 一句话复述"你要什么"（≤200 字，得让人**三秒判对错**） | v2 **必填非空**；空/超长 = 硬错。v1 的 `understood` 仍认、空着只提醒 |
| `anchors[]` | 具体参照物。`kind:"image"` = 参考图/帧；`kind:"text"` = 具体游戏名 / 前作 / 一句话观感 | v2 **至少 1 条**；`kind` 只认 image/text；`ref` 非空；**`kind:"image"` 的 ref 必须真实存在**（相对 intent 文件所在目录或绝对路径） |
| `anchors[].why` | 这条锚在给什么做参照 | 建议写；进台帐与报告 |
| `criteria[]` | 要对哪些指标下手：`{id, weight, target, anchor, userWords, howMeasured, why}` | **≤5 条**（超了硬错："轻合规"）；`id` 必须是 adapter 里真实存在的指标 id（写错硬错，绝不静默忽略） |
| `criteria[].anchor` | 这条判据指向参照物的哪个部位/哪个数 | v2 **每条必填**；写 `anchors[0]` 这种会校验下标（越界 = 硬错）；也可以是一句具体参照 |
| `criteria[].userWords` | **用户原话**（照抄，不翻译） | v2.1：与 `howMeasured` **至少写一个**；两个都空 = 硬错（"等于凭空编的指标"）。只有一个 → 能跑但 `degraded` |
| `criteria[].howMeasured` | **这个数怎么量**（别人照着能复算） | 同上。写"暂无口径 / 靠参考图对照"这类是**允许**的（诚实的说法），但该条 warn：「这条口径是'靠人看'，搜索不能用它当判据——考虑降权或改成可测量的量」 |
| `criteria[].dir` | **判据方向**：`lower`（下限型，越大越好）/ `upper`（上限型，越小越好）/ `two-sided`（区间型） | **pipeline 硬要求（0.30.0 起）**：带数值 `target` 的判据必须有 `dir`，缺了 = 硬错。为什么：曾把「p99 ≥0.045（下限）」写成「≤0.0523（上限）」，第 3 轮为一个不存在的上限牺牲了 p50 与 C4。`target` 的校验也随之按方向走：`lower` 只要求不低于某条实测 min，`upper` 只要求不高于某条实测 max，`two-sided` 才要求落在实测 [min,max] 内 |
| `criteria[].why` | 这条判据对应你说的哪句话 | 建议写；进台帐与报告 |
| `notWanted[]` | 明确**不要**什么 | 可以是空数组；**字段缺失 = 降级** |
| `freeVsFixed.fixed` | 哪些必须对（定死项） | 同上：可以是空数组，整个字段缺失 = 降级 |
| `freeVsFixed.free` | 哪些可以自由（别锁死） | 同上 |
| `howWeVerify` | 怎么算过：`{human:bool, metrics:bool, note}` | 两个 `false` 是硬错；字段缺失只 warn（"谁点头算过"没写进契约） |
| `uncertain[]` | 还没说清的地方 | 数组 |
| `confirm[]` | 要用户拍板的问题 | **≤3 条**（超了硬错）；`confirmed:true` 时仍有未答的 → 允许通过，warn"还有 N 条待确认问题没答，已按当前判据开跑" |
| `confirmed` | 用户点头了没有 | 必须是 `true`，否则拒跑 |
| `confirmedBy` / `confirmedAt` | 谁、什么时候确认的 | 进台帐（`confirmedBy @ confirmedAt`） |

> **方向别猜**：判据写成「区间」是最容易偷懒也最容易出错的一种。
> 参考实测出来的 4.25~7.50 只是**目标提示**，不是硬门——把它写成双侧上限，搜索会为了一个不存在的要求牺牲别的判据。
> 判断法：问自己「这个数**变大**算更好还是更坏」。变大更好 → `lower`；变小更好 → `upper`；两头都不行 → `two-sided`。
> 程序侧提示：`1.10-translate3` 出票时还会按判据文字做「本机位能不能测」的预检（地平线/天空/背景亮度/剖面/自相关），只提示不拦。

### 1.3 一条填好的小例子（命令链路、`examples/command-echo.json` 的指标）

```json
{
  "version": 2,
  "restate": "把包体积从 12 压回 10，同时别把 loss 推到 0（那是压过头）",
  "anchors": [
    { "kind": "image", "ref": "refs/ref-a.png", "why": "同类高评分的压缩曲线图" }
  ],
  "criteria": [
    {
      "id": "size", "weight": 2, "target": 10,
      "anchor": "anchors[0]：参考图里的体积刻度",
      "userWords": "用户原话：体积得压回 10，不然装不进镜像",
      "howMeasured": "解压后目录总字节数 ÷ 源目录总字节数",
      "why": "体积是你说的重点"
    },
    {
      "id": "loss", "weight": 1,
      "anchor": "anchors[0]：参考图里的画质下限",
      "userWords": "用户原话：别为了压体积把画质压没了",
      "howMeasured": "loss = 1 − 解压后与源逐字节相等的比例",
      "why": "别归零"
    }
  ],
  "notWanted": ["不要为了压体积把 loss 推到 0"],
  "freeVsFixed": { "fixed": ["体积上限 10"], "free": ["用哪条压缩通道压"] },
  "howWeVerify": { "human": true, "metrics": true, "note": "指标过闸后看一眼" },
  "confirm": [],
  "confirmed": true,
  "confirmedBy": "user",
  "confirmedAt": "2026-11-14T10:46:00+08:00"
}
```

过闸之后 `report.md` 顶部会长出这一段（`restate` 一行 + 锚几条 + 谁验收 + 每条判据的原话/量法 + 是否 v1 degraded）：

```
**需求转译（intent v2 · done）**

- **复述**：把包体积从 12 压回 10，同时别把 loss 推到 0（那是压过头）
- **锚**：1 条（image 1 / text 0） —— `refs/ref-a.png`
- **反例**：1 条：不要为了压体积把 loss 推到 0
- **自由度**：定死 1 条 / 自由 1 条；定死：体积上限 10；自由：用哪条压缩通道压
- **验收**：人眼 + 指标（两者都要）；指标过闸后看一眼
- **判据**：2 条（有原话 2 / 有量法 2 / 两者都无 0）
  - `size`（weight=2 target=10）：原话：用户原话：体积得压回 10，不然装不进镜像 / 量法：解压后目录总字节数 ÷ 源目录总字节数
  - `loss`（weight=1）：原话：用户原话：别为了压体积把画质压没了 / 量法：loss = 1 − 解压后与源逐字节相等的比例
- **确认**：`confirmed=true`（user @ 2026-11-14T10:46:00+08:00）
```

缺的那一项在报告里写成 **`⚠`**（`原话：⚠` / `量法：⚠`）—— 一眼就能看出哪条判据没有来路；
量法写了"靠人看"的那条后面还会多一句 `（⚠ 量法靠人看：搜索不能用它当判据，考虑降权或改成可测量的量）`。

同样的内容也落成机器可读的 `<out>/intent.summary.json`（台帐 `01-intent.json` 的 `artifacts` 指向它）。

### 1.4 v1 仍然能跑，但记 `degraded`

v1 = 没有 `version`、`criteria` 没有 `anchor` 的写法。它**照样能跑**（向后兼容），但：

- 打一条中文 warn：`这是 v1 intent（没有锚/反例/自由度），等于把审美全交给指标——建议升级到 v2`；
- 台帐 `01-intent.json` 的 `status` 记 **`degraded`**（不是 `done`），`reason` 写明缺什么；
  其中 v2.1 起还会补一句 **「也缺 userWords/howMeasured」**（v1 的 criteria 没有原话与量法）；
- `report.md` 顶部标 `**需求转译（intent v1 · degraded）**`。

升级只需要四件事：加 `version:2`、加 `restate`（把 `understood` 挪过来）、给每条 `criteria` 补 `anchor` 与一条 `anchors`、
给每条 `criteria` 补 `userWords` / `howMeasured`（至少一个，见 §1.8）。

### 1.5 为什么要这四样（它们不是装饰）

三份真实实验复盘的结论是「**提示词写法是第一杠杆，模型只抬上限不抬下限**」，而最大的坑是
**「指标替代审美」**：每轮都在追可数指标，单步都有"改进证据"，累积却把观感磨平。
只有"指标 + 权重 + 目标"的 intent 等于把这个坑**制度化** —— 所以 v2 补的四样全部来自那轮实验的实证：

| 补的东西 | 实证 | 不写会怎样 |
|---|---|---|
| **锚**（`anchors`） | "照着这张图调"比"要 3A 次世代"可执行得多；锚是唯一能把"像不像"钉住的参照物 | 只剩指标：它会把画面推向指标极值（更粗→糊成一片、更亮→烧白） |
| **反例**（`notWanted`） | 写"拒绝写实/PBR 连续渐变"比只写"要二次元"有效得多 | 搜索不知道边界，会往"指标最好看"的方向漂，正是要避免的那一侧 |
| **自由度 vs 定死项**（`freeVsFixed`） | 需求书把形态全锁成"严格直线"，锁出了僵直激光 | 该自由的地方定死 = 把搜索的手绑住，只能在一根线上做微小妥协 |
| **验收方式**（`howWeVerify`） | "谁来点头"不写进契约，指标过闸就被当成"成了" | 没人负责最后那一眼；指标更好看、人眼更难看，且没人有权说"不算" |

**一个纪律**：这四样**不参与距离计算**（`intent.summary.json` 里 `participatesInDistance: false`）。
锚一旦进距离就又变成指标 —— 那就绕回原点了。它们只做**记录与呈现**：写进台帐、写进 `report.md` 顶部。

### 1.6 v2 的硬上限（为什么是 5 条判据 / 3 条 confirm）

`criteria ≤ 5`、`confirm ≤ 3` 是"**轻合规**：写越厚，花在做到上的预算越少"。
判据越多，每条分到的搜索预算越薄；confirm 越多，越可能一条都答不上来。次要诉求写进
`anchors` / `notWanted` / `freeVsFixed`，别都塞进距离里。


**不同链路怎么知道有哪些 id**：`node harness/intent.mjs gate` 的报错和模板里都会列出来；
也可以看 `adapter.metrics[].id`（截图链路）或 `adapter.observe.metrics[].id`（命令链路）。
最省事的办法：**先不带 intent 跑一次** —— 引擎会写出 `intent.template.json`，模板的 `_说明` 里就写着这份 adapter 的指标 id。

**确认这一步不能省**：`confirmed: true` 是"用户看过并点头"，不是"agent 觉得自己懂了"。
引擎只认这一个布尔值 —— 它不判断你的转译写得好不好，只保证"没被点头的转译不会开跑"。


### 1.8 用户原话 + 怎么量（v2.1）：专治"编假指标"

**为什么**（外部实跑的一条硬教训）：**把用户嘴里的观感词（脆 / 糊 / 有主次）原样下发，等于没说**；
而为了显得专业去编一个看似精确的假指标（比如拿"色阶可数"当审美），会诱导搜索优化错方向 ——
历史上"越修越平"就是这么来的。

所以每条判据必须回答两个问题：**用户原话是什么**（来源可追溯）+ **这个数怎么量**（别人能复算）。

| 写的状态 | 引擎的反应 |
|---|---|
| `userWords` + `howMeasured` 都有 | 这条判据站得住；intent 照常 `done` |
| 只有一个（另一个空 / 没写） | **能跑**，但台帐 `01-intent.json` 记 `degraded`，`reason` 点名缺哪个：`缺 userWords（criteria: …）：这条判据没有用户原话，来源不可追溯` / `缺 howMeasured（criteria: …）：没人能复算这个数` |
| 两个都没有 | **硬错**：「这条判据没有任何用户原话/量法，等于凭空编的指标——要么写用户怎么说，要么写怎么量，要么删掉」 |
| `howMeasured` 里明说"靠人看"（暂无口径 / 靠参考图对照 / 靠人眼…） | **允许**（诚实 > 假装精确），但该条 warn：「这条口径是'靠人看'，搜索不能用它当判据——考虑降权或改成可测量的量」；台帐 basis 有一行「量法靠人看的判据：…」 |

**写对的样子**（对照着填）：

- `userWords` 照抄用户怎么说，**不要翻译**：他说"看着发虚、没有锐劲"，就写这句 —— 别写成"色阶可数"。
- `howMeasured` 写**别人能照着复算**的一句话："沿法线扫 alpha 25%→75% 的像素距离，越短越锐"。
  写不出来就老实写"暂无口径，靠参考图对照"，让 warn 提醒你这条不能进搜索 —— **别编一个数糊过去**。

**纪律**：`userWords` / `howMeasured` / `why` 三个字段**都不参与距离计算**，
只进台帐（`01-intent.json` 的 `decision.basis` 逐条记 `（原话：… / 量法：…）`，末尾一行
`判据来源：有原话 N 条 / 有量法 M 条 / 两者都无 0 条`）与 `report.md` 的 intent 摘要段（§6.1）。

**v1 老写法**不受这条硬错拦（向后兼容），但 `degraded` 的 reason 会补一句
「v1 intent 也缺 userWords/howMeasured（…）：判据没有用户原话，来源不可追溯；也没有量法，没人能复算这个数」。
