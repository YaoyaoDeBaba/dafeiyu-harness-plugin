# 怎么干活：开工跑道、派调查员、什么时候停

> **2026-11-16 架构调整（0.20.0）：流程不再写在 skill 里，由程序持有。**
> 两次受控实验证明：规范写在文档里只能「劝」，挡不住执行代理跳过闸门。
> 现在流程是 `harness/pipeline.mjs` 的节点表，**一个节点一个单职责子任务，下游只认上游的信号文件**：
>
```bash
node harness/pipeline.mjs status --run <run目录>   # 我在哪个节点
node harness/pipeline.mjs step   --run <run目录>   # 推进；exit 10 = 该派 agent 了（票已生成）
node harness/pipeline.mjs done   --run <run目录> --stage <id>   # 交活，程序核产物
```
>
> **skill 里只留「节点内怎么判断」**（量什么、判据怎么写、什么时候停）；流程顺序、闸门、下游等待，全部由程序管。

**什么时候读**：每次接手任务、准备开工前读一遍；犹豫「该不该停下来问人」「要不要自己搜一下」时再查。

> 这一篇把三件"纪律"放在一起（原来是两份文件，内容互相引用）：
> **① 开工跑道**（第一步做什么）→ **② 派调查员**（去哪儿找答案）→ **③ 什么时候可以停**（什么算做完）。

---


**什么时候读**：接到任务、准备开工前读一遍；或者在犹豫「该不该停下来问人」的时候查一次。

> 这份文件回答一个问题：**拿到一句需求之后，agent 该自己走到哪一步才允许停下来找人。**
> 背景（2026-11-16 实战）：做雷暴特效时，每一步都停下来等用户喊"继续"，
> 用户原话："嘴上说接着做不等我，但每次都停下来。" 这不是能力问题，是**没有把"到交付为止"当默认**。

## 一、默认值：推进到「可直接验收的产物」

不是"汇报进度"，是**交出一个能被人看着判断的东西**：图、对比条、指标表、可运行入口、证据包。
中间过程的每一步都要产出可见物，但**不因为产出了就停**——继续往下走，直到满足下面的停止条件。

## 二、只有三种情况允许停

| 类型 | 判据 | 例子 |
|---|---|---|
| **A 需要人的主观判断** | 这个取舍没有客观依据，只有人的偏好能定 | "云要压满上半屏还是只盖目标区"；"两根细雷还一根粗雷" |
| **B 需要人的操作** | 动作用户本人才能做 | 重启 Unity/DSH、授权、插设备、登录 |
| **C 不可逆或高风险** | 做错了收不回，或会波及别人 | 删数据、改主干、覆盖他人文件、发版 |

**不属于这三种的一律继续做**，包括：
- 参数怎么调（自己调，用指标说话）
- 用哪个现成组件（自己查，查到就用）
- 命名、目录、注释（自己定）
- 跑一次实验要多久（跑就是了）
- "要不要我再优化一下"（默认要，直到达到判据或撞到 A/B/C）

## 三、停下来之前必须已经产出东西

**空手问问题 = 庸臣。** 停下来时必须已经：
1. 交出了当前最好的一版（图 / 数据 / 文件），哪怕它不好看；
2. 说清差在哪（最好带数），而不是"我觉得还不行"；
3. 把要人拍板的那**一个**问题写清楚（一次最多两个），并且给出你的建议答案。

反例（2026-11-16 实际发生过的）：
- ✗ "云的亮度设 0.45 行不行？"——这是参数问题，自己调。
- ✗ "要不要继续？"——没有停止条件就不许问。
- ✗ 只贴一句"已修改，请查看"——没产物、没判断。

正例：
- ✓ 贴对照图 + 指标表 + "差距集中在光晕面积（0.7% vs 26%），我按这个方向再调一轮"。
- ✓ 贴三版对比 + "现在需要你定：要 A 还是 B，我建议 A，因为……"。

## 四、自查（每次回复前问三句）

1. 这次回复里有**新产物**吗（图/数据/文件/可运行入口）？没有 → 你在汇报，不在干活。
2. 停下来的理由属于 A/B/C 吗？不属于 → 继续做，别发这条消息。
3. 我有没有把"该我拍板的技术选择"包装成"请你确认"？有 → 自己拍，把理由写进产物。

## 五、和作业台的关系

作业台（`harness/ui.mjs`）是"让人随时能看、随时能拍板"的界面，**不是"每一步都要人点"的审批流**：
- 每轮结束就往 `rounds/NN.json` 写（截图 + 评审 + 改了什么）——人随时能看，但不需要他先点头；
- 只有撞到 A/B/C 时才等 `decisions.jsonl` 里的动作；
- 人点了「停在这里」→ 立刻停（这是 C 类），别问"确定吗"。

## 六、开工跑道：第一个动作是 preflight，不是读代码

2026-11-16 受控实验：派了一个上下文干净的执行代理，8 分钟里它读了全套规范、读了三个源码文件、
确认了 MCP 通道——但**一行产出都没有**，因为它不知道该从哪一步"开始做"。
工具没给跑道，代理只能在原地侦查。

所以：**接手任何带参考素材的需求，第一个动作固定是**

```bash
node harness/preflight.mjs --run <run目录> --ref <参考图或帧目录>
```

它会建骨架、把参考量出来的特征写进 `research.json.extracted[]`、生成 intent 空壳，
并打印"还差哪几步"，没到条件时以非零码退出。**preflight 没过，不许改工程文件。**

### 复用上一轮调研是允许的，但必须登记

不要为了"守规矩"重复调研；但也别把"上一轮查过"当成本轮的调研。正确做法：

```jsonc
// <本轮 run>/research.json
{ "reusedFrom": "../上一轮/research.json", "findings": [], "extracted": [], "changed": [] }
```

登记了，闸会去核对被引用那份的 findings 是否合格（能核、有 used、有 usedFor）；
指向不存在的文件直接硬错——**假复用不给过**。

### 什么时候算"可以动手改代码"

三个条件同时满足：preflight 退出码 0、`intent.confirmed === true`、criteria 每条都有 userWords 或 howMeasured。

# 派调查员：调研简报与验收



## 为什么要专门派一个人

2026-11-16 的教训：项目经理（主 agent）一边定判据一边写代码，「调研」被压缩成"随手搜一下"，
搜完不留产出、也不改变做法——最后我自己编了两条假设（"长直段"「折角太多」），**两条都被自己的实验证伪**。
所以：**调研必须是独立角色、独立产出、可验收**，不能是主 agent 的副产品。

## 派单方式

用 `subagent` 派（不要自己搜），名字起成 `res-<主题>`，模型选和主 agent 不同的（避免同一套偏见）。
一个调查员只查一个主题；主题大就拆成两个并行。

### 派单模板（照抄改）

```
你是一名技术调查员。任务：**只做调研，不写代码、不改文件**。
## 要查什么
<3~5 条具体的检索方向：算法名、开源实现、已知失败形态>
## 硬要求
- 至少 6 个来源，优先能读到代码的开源实现；每条给 URL
- 每条回答：它解决什么 / 具体怎么做（含参数或公式）/ 哪部分能直接抄
- 查不到就写「没找到」，**不许编造 URL、作者、年份**
- 输出 JSON：{ "findings": [ { "title","url","kind","what","how","reusable" } ], "gaps": [] }
```

## 验收标准（写进 research.json，由调研闸强制）

| 项 | 要求 | 为什么 |
|---|---|---|
| `extracted[]` | 非空，每条含 what / value / source | 参考图必须被**量过**（用 `ref-probe`），不是凭感觉 |
| `findings[]` | **≥2 条带 http(s) URL** | 「调研过」的证据是外部来源，不是自言自语 |
| `findings[].used` | **≥1 条 true** | 调研必须真的改变了做法，否则是装饰 |
| `falsified` | 被实验否定过的假设要标出来 | 防止把"我猜的"当成"查到的" |

## 常见退化（出现任何一条就是没干活）

- 只写结论不写来源（"业界通常用中点位移法"——哪来的？）
- 把主 agent 的猜测抄进 findings 当调研结果
- 搜了 3 个链接但一条 used 都没有（调研没落地）
- 用"参考图看起来是…"代替量测（这正是实战翻车的原因）

## 派单契约：规则写在派单那一刻，不写在文档里

2026-11-16 两次受控实验的结论：
- 第一次：执行代理读了全套规范、读了源码，**8 分钟零产出**（没有起飞跑道）；
- 第二次：加了 `preflight` 之后，它仍然**手写了一个 python 量图脚本、跳过 preflight、直接改工程文件**。

规范写进 skill 不等于会被执行。**靠得住的做法是派单者把开场指令写进 prompt**：

```text
你是一个执行 agent。第一步固定运行：
  node <包>/harness/preflight.mjs --run <run目录> --ref <参考素材>
它退出码非 0 就按它列的清单补齐（量参考 → 派调查员 → 填 intent），补齐之前不许改任何工程文件。
```

同时派一个**观察员**核对产物（不是核对自述）：

| 核对项 | 判据 |
|---|---|
| 走了跑道 | `research.json.extracted[]` 非空 |
| 调研有外部来源 | findings ≥2 带 URL、≥1 条 kind=opensource/paper |
| 调研落地 | 每条 used 都有 `usedFor` |
| 先判据后代码 | `intent.json` 的 mtime 早于被改的工程文件 |

**这道闸与执行器无关**：不管用 `iter.ps1`、`cmdloop.mjs`，还是你自己拿 MCP / 脚本手搓一条链路，开工前都要过同一道检查：

```bash
node harness/preflight.mjs --run <run目录> --check    # 只判定，不写任何文件；0=可开工 / 3=调研没完 / 4=intent 没写完
```

2026-11-16 第二次受控实验的教训：因为引擎的 web 执行器**接不上 Unity 宿主**（三个适配器都 `runnable:false`），
执行代理就自己搓了一条 MCP + Python 的链路——**而闸门原来只挂在引擎链路里**，于是全被绕过。
现在闸门只看 run 目录的状态（`extracted` / `findings` / `intent.confirmed`），跟你怎么执行没关系。
